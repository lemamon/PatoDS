# monorepo

## DECISION
Three parts. (1) pnpm 11.x with an exact version (11.28.6, `latest-11` today), pinned in `packageManager`/`devEngines.packageManager` with `pmOnFail: error`. (2) Turborepo 2.11.x (turbo@2.11.10 exact, a root devDependency via catalog). (3) Self-hosted remote cache ducktors/turborepo-remote-cache v2.14.x (MIT, image pinned by digest), with AUTH_MODE=jwt validating the GitHub Actions OIDC token: read for any job in the repository, write only for the `job_workflow_ref` of the protected branch's workflow. Layer boundaries: versioned file = root `turbo.json` (`boundaries.tags` with layers and allowed edges) + `tags` in each package's `turbo.json`. They are verified in CI by `turbo boundaries` and by a pnpm manifest check (`pnpm ls -r --prod --json`) for the rule "tools depend on the UI only as a devDependency". Toolchain: Node.js 24.x LTS (24.22.1, `.node-version`). TypeScript ~6.0.3 as the single emit and API compiler for the tools. TypeScript 7.0.x enters only as the "latest" axis of the ENG-08 matrix, in a fixture project that consumes the tarballs.

## RATIONALE
Facts verified on 2026-10-21:
- pnpm: the current major is 12 (rewritten in Rust; GA on 2026-08-26, dist-tag latest = 12.14.0). It keeps pnpm 11's commands, settings, lockfile and layout, but had about 15 minors in 8 weeks and still gets new features (task scheduler in 12.1, remote task cache in 12.12). pnpm 11 (GA on 2026-04-28) is still maintained (11.28.7 shipped today) and is the mature line.
- Turborepo: 2.11.10 (MIT). Distributed as optional per-platform binaries, with no install scripts. Turborepo's own repository uses pnpm 12 with lockfileVersion 9.0, the same format as pnpm 11, so compatibility is proven.
- Nx: 23.3 (MIT). The `nx` package has a `postinstall`. The self-hosted bucket caches have been deprecated since 2026-05-21 because of CVE-2025-36852, which has no fix. The path Nx recommends is Nx Cloud (proprietary).

Why pnpm 11:
- ENG-24: `strictDepBuilds: true` (default in 11) + the `allowBuilds` map in `pnpm-workspace.yaml`, which is the versioned allowlist. `onlyBuiltDependencies` was removed in 11. A package with a script outside the map makes the install exit with an error, and a deliberate fixture proves it.
- ENG-16: `pnpm install --frozen-lockfile` (or `pnpm ci`). An out-of-date lockfile fails.
- ENG-08 and ENG-25: `catalog`/`catalogs` with `catalogMode: strict` give a single version per dependency, and named catalogs serve the React/Vue floors in the matrix. `catalog:` and `workspace:` are rewritten on pack/publish. CODEOWNERS on `pnpm-workspace.yaml` covers ENG-25.
- Supply-chain defaults already active in 11: `minimumReleaseAge` of 1 day and `blockExoticSubdeps: true`. We will also enable `trustPolicy: no-downgrade`.
- Native commands: `pnpm sbom` (CycloneDX/SPDX, ENG-19) and `pnpm licenses list --json` (ENG-21).
- QA-06: `pnpm pack` generates the tarballs that the example apps consume.
- pnpm 12 is left for later. The 11→12 migration is cheap (same lockfile and same settings) and 12 is still stabilizing. We prefer maturity on a base with determinism and supply-chain gates.

Why Turborepo:
- ENG-02: `turbo run <tasks> --affected` with `TURBO_SCM_BASE` = the PR base SHA selects the changed packages and their dependents. For the full run: `globalDependencies` lists `.node-version`, `pnpm-workspace.yaml`, `.github/workflows/**` and `.github/actions/**` (root `package.json` and the lockfile are already global by default). A scope step in CI compares `git diff --name-only BASE...HEAD` against that same versioned list and, on a match, runs without `--affected`. The `futureFlags.affectedUsingTaskInputs` flag does the same natively, but it is experimental, so it stays optional. The daily cron on main runs without `--affected` and with `--force` on the test tasks.
- ENG-03: the remote cache protocol is an open OpenAPI specification, which allows a self-hosted server. TRRC in JWT mode has separate read and write permissions per claim. Configuration: `JWKS_URL`/`JWT_ISSUER` from GitHub, `JWT_SCOPE_CLAIM=repository`, `JWT_READ_SCOPES=JWT_WRITE_SCOPES=<org>/<repo>`, `JWT_ROLES_CLAIM=job_workflow_ref`, `JWT_WRITE_ROLES=<org>/<repo>/.github/workflows/<main>.yml@refs/heads/main`, `JWT_TEAM_CLAIM=repository_owner`.
  - PRs, pushes to other branches and the merge queue read, but get a 403 on PUT. The client also uses `--cache=local:rw,remote:r` off main.
  - There is no fixed secret, because the credential is federated (ENG-13). A fork PR gets no id-token and runs with local cache only (ENG-14).
  - The ENG-03 deliberate test is a PUT from a PR, which must get a 403. Proof of 100% hit rate comes from `turbo run --summarize` (per-task cache status).
- Determinism: `envMode: strict` (default) restricts the task environment to the declared variables. This avoids contaminated cache keys. The TOK-05/IA-04 byte-for-byte check runs with `--force`, without cache.
- ENG-01: `turbo boundaries` fails on an import of a file outside the package and on an import of a package not declared in `package.json`. That is, it guarantees imports ⊆ manifest edges. The layer tags (tokens, core, frameworks, icons, catalog, lint, codemods, mappings, tools) with `dependencies.allow` also apply to transitive dependencies. Turbo does not distinguish a dependency from a devDependency, so the manifest check (a script with a unit test, QA-02) reads the same tags and fails if a `tools` package has a UI package in its `--prod` closure. Together, the two checks give imports ⊆ manifest ⊆ edges allowed per type. Deliberate violations per edge go into CI and into ACE-08.
- Supply chain: zero install scripts in turbo and in pnpm-as-a-dependency, and MIT on the chosen pieces (pnpm, turbo, TRRC).

Node 24: it is the LTS line today (Krypton, EOL 2028-04-30) and runs pnpm 11 (which requires ≥22.13). Node 26 only becomes LTS on 2026-10-28, so today it does not meet the "Node on LTS" assumption.

TypeScript 6.0: TS 7.0 (GA on 2026-07-08) has no programmatic API until 7.1. Microsoft advises Vue/Volar projects to stay on 6.0, and typescript-eslint 8.72 requires `typescript <6.1.0`. A single compiler (6.0) keeps emission deterministic and avoids the `tsc` binary conflict between 6 and 7.

Assumed premises: GitHub Actions as CI (inferred from ENG-18), protected branch `main`, single version (current assumption; the versioning tool is another ADR), `<prefixo>` as a marker.

## ALTERNATIVES
- pnpm 11 + Nx 23 (cache via Nx Cloud or self-hosted): The strengths are real: a stable @nx/enforce-module-boundaries ESLint rule and Nx Cloud read-only tokens that isolate writes. But a remote cache that meets ENG-03 requires Nx Cloud (proprietary SaaS; on-prem only with an Enterprise license). The self-hosted plugins (@nx/s3-cache, gcs, azure, shared-fs) have been deprecated since 2026-05-21 and are vulnerable to CVE-2025-36852 (CREEP), with no possible fix. A self-hosted server via OpenAPI is classified by Nx itself as 'high-risk'. Besides, the `nx` package has a postinstall and was compromised through exactly that postinstall in Aug 2025 (s1ngularity). Majors ship every 6 to 8 months (22 in Oct 2025, 23 in Jun 2026, 24 in rc), with frequent migrations, and the tool is heavier (daemon, plugins, inferred tasks).
- pnpm 12 (Rust rewrite, dist-tag latest) instead of pnpm 11: GA 8 weeks ago (2026-08-26), with about 15 minors and features still landing (scheduler, remote task cache, toolchain management). It keeps 11's settings and lockfile, so migrating later costs little. Left for when it stabilizes or when 11 leaves maintenance.
- pnpm alone as the orchestrator (`--filter "...[origin/main]"`; pnpm 12.12 task cache): pnpm 11 has no task cache (fails ENG-03). The pnpm 12 remote task cache shipped on 2026-10-10 and is immature, with no documented model for write-only-by-protected-branch. It also has no boundary checking.
- moon 2.x (moonrepo): MIT, in Rust, with stable layer and tag constraints (`enforceLayerRelationships`, `tagRelationships`). But v2 has existed only since 2026-02. The remote cache uses the Bazel Remote Execution API, and the docs say TLS/mTLS support is 'very unstable' and give no guidance on read-only PRs. Authentication is by bearer/header, i.e. a fixed secret, which conflicts with ENG-13. The community is smaller, there is one moon.yml per project, and a custom toolchain manager that overlaps pnpm/devEngines.
- Rush 5.x (Microsoft): Mature and MIT. The lockStep version policy matches the single-version premise, and cache writes are controlled by `isCacheWriteAllowed`/`RUSH_BUILD_CACHE_WRITE_ALLOWED` (Azure/S3). But Rush wraps pnpm (rush install over a workspace generated in common/temp), which duplicates configuration and delays adopting pnpm 11 features (allowBuilds, catalogs). It has no built-in tag-based boundary lint, a heavier operating model, and is little used in React/Vue DS.
- Vercel managed Remote Cache (with OIDC) instead of the self-hosted TRRC: It is free and accepts OIDC. But the documented OIDC policy only restricts which repository/branch/workflow gets access, without distinguishing read from write. So a read-only PR would depend only on the client flag `--cache=remote:r`, which is not enforced on the server, or the PR would have no cache. The build artifacts would also leave the requester's infrastructure.
- GitHub Actions cache as the turbo backend (via a third-party action): Branch-scope isolation stops a PR from poisoning main. But the PR still writes to its own scope, which does not meet the literal 'read only' of ENG-03. It requires a third-party action with ACTIONS_RUNTIME_TOKEN and has a per-repository storage limit.
- Boundary lint with eslint-plugin-boundaries or dependency-cruiser instead of `turbo boundaries`: They are stable and MIT, but they look only at imports, not at manifest edges. Classifying a workspace package (via pnpm's symlink) as dev or prod is not documented. They stay as plan B if `turbo boundaries` (experimental) changes; the pnpm manifest check still holds in both cases.
- npm or Yarn 4 workspaces: They do not bring, at the same level and by default, the set pnpm 11 offers out of the box (strictDepBuilds + allowBuilds, minimumReleaseAge, blockExoticSubdeps, trustPolicy, catalogs, native `pnpm sbom` and `pnpm licenses`). Meeting ENG-24, ENG-19 and ENG-21 would require extra tools.

## REQUIREMENT FIT
- ADR-09: A single monorepo with pnpm workspaces (packages/*, tools/*, apps/*) and automatically verified layer boundaries. The decision implements ADR-09 without changing it, so it needs no change request.
- ENG-01: The versioned file is the root `turbo.json`, with `boundaries.tags` listing the layers (tokens, core, frameworks, icons, catalog, lint, codemods, mappings, tools) and the allowed edges. `turbo boundaries` fails on a forbidden edge, an import outside the package, or an undeclared dependency. A manifest check (`pnpm ls -r --prod --json`, a script with a unit test) fails if a `tools` package has UI outside devDependencies. There is a deliberate-violation fixture per edge, re-presented in ACE-08 for each new layer.
- ENG-02: `turbo run lint typecheck test build --affected` with `TURBO_SCM_BASE` = the PR base SHA, and a checkout with enough history (a shallow checkout makes turbo treat everything as changed). A change in the lockfile, root `package.json`, `.node-version`, `pnpm-workspace.yaml`, `turbo.json` or `.github/**` triggers a full run: a versioned list in `globalDependencies` + a scope step in CI. Daily cron on main without `--affected`. The CI log and `--summarize` show the scope.
- ENG-03: Self-hosted TRRC with AUTH_MODE=jwt over GitHub OIDC. Read requires the `repository` claim. Write requires `job_workflow_ref` = the main workflow on refs/heads/main, so a PR, a push on another branch and the merge queue get a 403 on PUT. The client also uses `--cache=local:rw,remote:r` off main. The deliberate test is a PUT from a PR, expecting a 403. Re-running with no change proves 100% hit rate through the `--summarize` JSON.
- ENG-16: CI with `pnpm install --frozen-lockfile` (or `pnpm ci`). A deliberate run with a changed package.json and no lockfile fails with ERR_PNPM_OUTDATED_LOCKFILE.
- ENG-24: `strictDepBuilds: true` and the `allowBuilds` map in `pnpm-workspace.yaml` form the versioned allowlist. Packages with a script are explicitly denied (`false`) or allowed with a justification. A fixture dependency with a postinstall outside the map makes the install exit with a non-zero code.
- ENG-25: Dependencies and versions centralized in `catalog` in `pnpm-workspace.yaml` (`catalogMode: strict`). CODEOWNERS on that file and on the package.json files requires owner approval.
- ENG-13: The remote cache uses a federated credential (GitHub OIDC), with no fixed secret in the inventory. `TURBO_REMOTE_CACHE_SIGNATURE_KEY` is not used: the documentation itself says it is not a security feature, and it would require a fixed secret.
- ENG-14: Fork PRs get no OIDC token or write secrets and run with local cache only. Cache writing is tied to the main workflow.
- ENG-07: The chosen direct build dependencies (turbo 2.11.10, typescript 6.0.3) are not deprecated in the registry today. pnpm enters via `packageManager`, not as a dependency.
- ENG-08: Node 24.x LTS and TypeScript 6.0 toolchain. The matrix tests the floor (working assumption: Node 24 and TS 6.0) and the latest version (Node 26 LTS from 2026-10-28; TS 7.0.x in a fixture that consumes the tarballs). Named pnpm catalogs pin the React/Vue floors. `engines` and `peerDependencies` are aligned to the tested floor.
- ENG-19: `pnpm sbom --sbom-format cyclonedx|spdx --split` (since pnpm 11) generates one SBOM per published package.
- ENG-21: `pnpm licenses list -r --json` feeds the check against the versioned license policy. This decision's tools are MIT (pnpm, turbo, TRRC) or Apache-2.0 (TypeScript).
- ENG-17: `pnpm pack` produces the tarball the allowlist check inspects. The `workspace:` and `catalog:` protocols are rewritten on pack/publish.
- ENG-18: The design does not depend on third-party actions for the cache: the OIDC token is obtained via ACTIONS_ID_TOKEN_REQUEST_URL. Node and pnpm setup via SHA-pinned actions.
- QA-06: The example apps install the tarballs generated by `pnpm pack`, never the source code via `workspace:`.
- QA-02: The custom orchestration scripts (the layer manifest check, the ENG-02 scope step) have unit tests.
- TOK-05 / IA-04: `envMode: strict` restricts the task environment to the declared variables. A frozen lockfile and a pinned toolchain (exact Node, pnpm, turbo, TS) guarantee identical inputs. The byte-for-byte check runs with `turbo run --force`, so the cache does not mask non-determinism.

## RISKS
- `turbo boundaries` is still experimental (since 2.4, Jan 2025, and still in 2.11). Mitigation: turbo pinned to an exact version, deliberate-violation fixtures in CI detect a behavior change, and the manifest check is independent of Turbo. Plan B: eslint-plugin-boundaries (MIT) for the import level.
- pnpm 11 may leave maintenance now that 12 is latest. Mitigation: 12 keeps settings and lockfile. Migration planned via a toolchain PR (which triggers a full run by ENG-02) when 12 stabilizes or when 11 stops getting fixes.
- GitHub OIDC token lifetime: sources diverge (5 min vs about 1 h). If it is shorter than the job duration, late reads and writes fail with 401. Turbo treats this as a miss or warning, and the build does not break. Mitigation: measure exp−iat in the proof of concept. If needed, use a minimal local proxy in the job that renews the token on every request (tested, no secret).
- Misconfigured claims can leak write permission. For example, `pull_request_target` runs with main's ref. Mitigation: the write role is tied to the `job_workflow_ref` of a push-and-cron-only workflow on main, there is a workflow lint forbidding `pull_request_target`, and a deliberate PUT-from-PR test must get a 403.
- Operating the TRRC (availability, storage, patches, retention) is the vendor's or platform's responsibility. If it goes down, the run continues with local cache, slower and with risk to the 15-min pipeline median. The image is pinned by digest and goes into the SBOM and the inventory.
- Fork PRs run without the remote cache, so CI is slower for external contributions.
- Turbo's `--affected` is per-package granular. Lockfile or toolchain changes trigger a full run by design, at a CI cost.
- TypeScript: 7.0 has no API until 7.1, and typescript-eslint 8.72 requires `typescript <6.1.0`. Staying on 6.0 gives up tsgo speed. 6.0.3 gets few fixes, and @microsoft/api-extractor embeds TS 5.9.3, which may delay support for new syntax in the API reports (QA-08).
- Node 24 entered Maintenance LTS on 2026-10-20. The switch to 26 (Active LTS on 2026-10-28, EOL 2029-04-30) should happen within about 12 months. Node 22 has EOL on 2027-04-30, which is why it was not proposed as the floor.
- Turbo collects anonymous telemetry by default. Mitigation: `TURBO_TELEMETRY_DISABLED=1` in CI and in the repository docs; `updateNotifier: false` in pnpm.
- Turborepo is governed by a single vendor (Vercel). The MIT license and the open OpenAPI cache spec reduce lock-in.

## OPEN QUESTIONS
- Platform: confirm GitHub (Actions) as the repository and CI. The ENG-03 and ENG-13 design uses GitHub OIDC, and the premise was inferred from ENG-18.
- Platform: authorize and indicate where to host the remote cache server (container + S3, GCS or Azure bucket): cloud account, region/data residency and artifact retention. The SaaS alternative (Vercel) does not enforce read-only on the server.
- Engineering (the 'Minimum versions' premise): confirm the working floor assumptions: Node 24 (22 has EOL on 2027-04-30, close to 1.0, and raising `engines` later forces a major) and TypeScript 6.0 (7.0 has no API for Vue/typescript-eslint). The consuming apps' version inventory (MIG-01) should inform this decision.

## ADR
Package manager, task orchestrator and remote cache for the monorepo: pnpm 11 + Turborepo 2 + a self-hosted cache with OIDC and versioned layer boundaries

# VERIFICATION: needs_changes
- [major] CLAIM: ENG-01: `turbo boundaries` fails on an import outside the package and on an undeclared package, guaranteeing imports ⊆ manifest ⊆ allowed edges; eslint-plugin-boundaries/dependency-cruiser stay only as plan B.
  PROBLEM: Turborepo's source code (crates/turborepo-boundaries/src/lib.rs) sets `.vue` and `.svelte` files apart and only emits the warning "vue files are currently not supported, boundaries checks will not apply to them". The globs also do not include `.mts`/`.cts`. In a DS where the Vue layer, idiomatic per ADR-01, will be written in SFC, the import check (file outside the package, undeclared package) does not run on the Vue layer. The tag rules still hold, because they use the package.json graph. But a `../../react/src/x` or an import of a root devDependency inside a .vue passes without error. The "imports ⊆ manifest" chain claimed for ENG-01 is false for one of the two frameworks.
  CORRECTION: Make mandatory, not plan B, an ESLint import check that covers `.vue` via vue-eslint-parser (MIT, 10.4.1): eslint-plugin-import-x 4.17.1 with `no-relative-packages` and `no-extraneous-dependencies`, or eslint-plugin-boundaries 7.2.1. Run it in the same lint as A11Y-03. Keep `turbo boundaries` for the tag rules over the package graph and the pnpm manifest check for dev vs prod. The deliberate-violation fixtures per edge must exist in .ts/.tsx and in .vue.
- [major] CLAIM: ENG-08: the matrix tests the floor, with a working assumption of Node 24 and TS 6.0; `engines`/`peerDependencies` aligned to that floor.
  PROBLEM: The current "Minimum versions" premise is "Majors with each project's official support; ... Node on LTS". The result also mixes the repository toolchain's Node with the published consumption floor.
  CORRECTION: Separate the two. The repository toolchain stays on Node 24.x (.node-version), which is acceptable. The `engines` and matrix floor follows the current premise: Node 22 LTS, and Node 26 as "latest" from 2026-10-28. Raising the floor to 24 (argument: 22's EOL near 1.0, and raising engines later forces a major) stays a question for Engineering, with MIG-01 as input. TS 6.0 enters only as a provisional value for `<version>`, explicitly marked.
- [major] CLAIM: ENG-03: the GitHub OIDC token is used directly as the TRRC credential (AUTH_MODE=jwt); the token-renewing proxy is only an "if needed" mitigation, after measuring exp−iat.
  PROBLEM: Turbo reads TURBO_TOKEN once per run. The example token in GitHub's documentation has exp−iat = 300 s, and Spacelift support reports 5 min. With the 15-min pipeline median, PUTs made at the end of the run on main tend to get 401. Turbo treats this as a warning, so main's cache stays incomplete and the ENG-03 100%-reuse criterion fails silently. The expected case is that the proxy is needed, and it is sensitive custom code: on main, it issues a write credential. The configuration also omits JWT_AUDIENCE and uses mutable claims (`repository`, `repository_owner`) instead of IDs.
  CORRECTION: Put in the base design a minimal local sidecar, bound to 127.0.0.1, used via `--api`/`remoteCache.apiUrl`, that requests a fresh OIDC token per request via ACTIONS_ID_TOKEN_REQUEST_URL. It needs a unit test (QA-02), and envMode strict must keep hiding ACTIONS_ID_TOKEN_REQUEST_* from the tasks. Set JWT_AUDIENCE with a dedicated audience and prefer `repository_id`/`repository_owner_id` as the scope and team claims. The ENG-03 proof of concept must include a job longer than 15 min that writes everything and a re-run with a 100% hit rate.
- [minor] CLAIM: TRRC v2.14.x is mature and active enough to be the ENG-03 anti-poisoning control.
  PROBLEM: The roles claim parser and JWT_TEAM_CLAIM, which are exactly the features the design depends on, landed on 2026-09-17 (v2.13/v2.14, about 5 weeks ago). The project in practice has a single human maintainer (the other contributions come from bots). The result does not record this risk, even though it is the central security control.
  CORRECTION: Record the maturity and bus-factor risk. The deliberate PUT-from-PR test, which must return 403, stays a recurring check, not only at acceptance. Define a plan B: two instances over the same bucket, one READ_ONLY=true for PRs and another write instance reachable only from a protected main environment. Alternative: a minimal self-hosted server, per the OpenAPI, that refuses overwrites (409), as Nx recommends for self-hosted servers.
- [minor] CLAIM: Per-package tags + `boundaries.tags` in the root turbo.json are enough as the versioned layers file.
  PROBLEM: A package without `tags` escapes its own layer's `dependencies` rules. Besides, Turborepo accepts `@boundaries-ignore` comments that suppress the violation in the PR itself, with no formal exception. The constitution requires every violation to have a foreseen and recorded exception.
  CORRECTION: The manifest check script must fail if any workspace package does not have exactly one layer tag declared in the root turbo.json. A lint must block `@boundaries-ignore` (and ESLint equivalents) outside a versioned exceptions registry with an owner.
- [minor] CLAIM: Exact pins: turbo@2.11.10 (and pnpm 11's default settings, with minimumReleaseAge of 1 day).
  PROBLEM: turbo 2.11.10 was published on 2026-10-20T20:35Z. At the decision date it is less than 24 h old, so the very `minimumReleaseAge: 1440` recommended refuses the install. The decision contradicts its own supply-chain policy.
  CORRECTION: Declare the rule that every pin must have age ≥ minimumReleaseAge. Today that means using 2.11.9 or waiting for the window before pinning 2.11.10. Pin updates only via a toolchain PR, and do not open an exception in `minimumReleaseAgeExclude` for turbo.
- [minor] CLAIM: ENG-08: TS 7.0.x as the "latest" axis in a fixture project that consumes the tarballs.
  PROBLEM: Per the TS 7.0 announcement, Vue/Volar projects must stay on 6.0 (vue-tsc depends on the API, which only arrives in 7.1). The Vue SFC fixture does not run typecheck on TS 7. The result does not say which checks actually run on the 7 axis.
  CORRECTION: Specify that, on the TS 7 axis, tsc 7 runs on the React fixture and on the Vue package's .ts consumers. SFC typecheck (vue-tsc) stays on TS 6.0 until the 7.1 API. Record this as a limitation of the "latest" axis for Vue.
- [minor] CLAIM: pnpm 12 was deferred only for maturity (about 15 minors in 8 weeks).
  PROBLEM: The result fails to mention a relevant supply-chain fact: the `pnpm` npm package 12.x (12.14.0, 12.15.0) declares `preinstall`/`postinstall: node install.js`, while 11.x has no scripts. This weighs on the current choice and on the migration path.
  CORRECTION: Add this fact to the pnpm 12 rejection and to the migration plan. Install pnpm only via a SHA-pinned action or via `packageManagerDependencies` with integrity in the lockfile, never via `npm i -g pnpm@12`.

## REVISED DECISION
Keep the stack choice, with adjustments. (1) pnpm 11.28.x with an exact version, pinned in `packageManager`/`devEngines.packageManager` with `pmOnFail: error` and installed by a SHA-pinned action. Use strictDepBuilds + allowBuilds, `--frozen-lockfile`, strict catalogs, minimumReleaseAge 1440, blockExoticSubdeps and trustPolicy no-downgrade. Rule: every pin must have age ≥ minimumReleaseAge. pnpm 12 is deferred; add to the justification that its npm package has pre/postinstall. (2) Turborepo 2.11.x with an exact version mature enough for minimumReleaseAge, `--affected` with TURBO_SCM_BASE, globalDependencies + a scope step for a full run, envMode strict, telemetry off. (3) ENG-01 in three mandatory checks, all with violation fixtures in .ts and in .vue: (a) `turbo boundaries` for the tag rules over the package graph; (b) ESLint import rules that cover `.vue` via vue-eslint-parser (eslint-plugin-import-x `no-relative-packages`/`no-extraneous-dependencies`, or eslint-plugin-boundaries), because turbo boundaries ignores .vue/.svelte/.mts/.cts; (c) a pnpm manifest check with a unit test, which fails with UI in the `--prod` closure of `tools` packages, with a package lacking exactly one layer tag, and with `@boundaries-ignore` outside the exceptions registry. (4) ENG-03 with a self-hosted TRRC (MIT, image pinned by digest), AUTH_MODE=jwt over GitHub OIDC, a dedicated JWT_AUDIENCE and immutable claims (repository_id/repository_owner_id). Write only for the `job_workflow_ref` of the main workflow. The base design includes a local token-renewal sidecar, with a unit test, because OIDC tokens are expected to last about 5 min. The recurring PUT-from-PR test must get a 403. Plan B: a pair of READ_ONLY and write instances, or a minimal self-hosted server that responds 409 for an existing key. (5) Repository toolchain on Node 24.x LTS and TypeScript 6.0.x as the single emit compiler. The `engines` and ENG-08 matrix floor follows the current premise: Node 22 LTS, with Node 26 LTS from 2026-10-28 as the latest. TS 6.0 as the provisional value for `<version>`. The TS 7 axis only for tsc on the React and .ts fixtures; vue-tsc on TS 6. Questions for the requester: raise the floor to Node 24, set the TS floor (with MIG-01 as input), confirm GitHub Actions, and the cache server's hosting/retention.
