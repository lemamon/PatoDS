## 2. Published files

| Generated file | Import by the app | Content | Count |
| --- | --- | --- | --- |
| `dist/css/base.css` | `@<prefixo>/tokens/css/base.css` | Layer-order declaration; shared primitives; mode toggles with the default mode; token resolver | One |
| `dist/css/brand-<id>.css` | `@<prefixo>/tokens/css/brand-<id>.css` | Layer-order declaration; one rule for brand `<id>` with its exclusive primitives, the brand-axis tokens and the brand-mode sources | One per `brand` modifier context of `src/tokens.resolver.json` |

The `base.css` contains no value exclusive to any brand, and each `brand-<id>.css` contains only
selectors of its brand (operational definitions in §10).

Usage rules, normative for apps and tests:

- **U-01** The app MUST import `base.css` and at least one brand file. Neither works on its own.
- **U-02** If the app does not import the default brand's file, it MUST mark the document root with
  `data-<prefixo>-brand` equal to an imported brand (FR-013). Without it, the brand tokens have no
  applicable declaration, and the configuration is not supported.
- **U-03** The import order between `base.css` and the brand files, and among brand files, does not
  change the result (§5).
- **U-04** The app MAY import several brands. The default brand, if imported, applies in scopes without
  a brand attribute; the others only take effect in scopes that select them.
- **U-05** The token CSS is always generated (FR-015). `packages/tokens/dist/` is in `.gitignore`,
  `pnpm check:drift` fails if any generated file is versioned, and `pnpm check:scan` flags a custom
  property declaration with a literal value outside the token source.
- **U-06** Adding a brand creates a new `brand-<id>.css` without changing the `package.json`, because
  the `./css/brand-*.css` export already covers it (FR-009, SC-005). The regenerated API report also
  changes ([esm-output.md](esm-output.md), §11.3).

## 3. Layer and single source of the layer order

- **L-01** Every token style rule sits inside `@layer <prefixo>.tokens { … }`. No token file has a
  rule outside that layer, so that app CSS outside a layer wins without a specificity dispute (ADR-03).
- **L-02** Every published file, after the header comment, begins with the same layer-order
  declaration, byte-for-byte identical in `base.css` and in every brand file. In Phase 1 the
  declaration is `@layer <prefixo>.tokens;`. The layer order is fixed by the first appearance, and any
  file may be loaded first; redeclaring already-known layers does not change the order.
- **L-03** The ordered list of PatoDS layers is a single fact with a single source, maintained by the
  lowest layer (tokens), on which the core may depend and which never depends on the core.
  Location decided in the plan (research.md, D8): versioned file `packages/tokens/src/layers.json`, in
  the form `{ "order": ["<prefixo>.tokens"] }`. The generator emits the L-02 declaration from it and
  copies the list into the `layerOrder` field of `dist/meta/tokens.manifest.json`.
- **L-04** Coordination with MIG-14 (Phase 2): the style core adds its layers to that same file, after
  `<prefixo>.tokens`, and emits the same declaration by reading `layerOrder` from the manifest. The CI
  check of MIG-14, which compares the documented list with the `@layer` declaration of the distributed
  CSS, MUST also cover `base.css` and every `brand-<id>.css`. In Phase 1, the `css-layer` check (§13)
  compares the emitted declaration with the source.
- **L-05** `<prefixo>.tokens` is always the first item of the list (lowest layer). The names follow the
  form `<prefixo>.<kebab-segment>`. Reordering, renaming or removing a layer is an incompatible change
  (major); adding a layer at the end is compatible (classified in the API report,
  [esm-output.md](esm-output.md), §11).
- **L-06** No token declaration uses `!important`, and no file uses `@import`, `@media`, `@supports`,
  `@container`, `@scope` or `@property`.

## 4. Where each token type is declared

"Brand X rule" is the rule of `brand-X.css` whose selector is `[data-<prefixo>-brand="X"]`; in the
default brand's file, and only there, the selector is `:where(:root), [data-<prefixo>-brand="X"]`.

| Token type (data-model) | File | Rule | Value form |
| --- | --- | --- | --- |
| Shared primitive | `base.css` | `:where(:root)` | Serialized literal (§11) or `var()` of another `base.css` primitive |
| Primitive exclusive to brand X | `brand-X.css` | Brand X rule | Literal or `var()` of a primitive from `base.css` or from the same file |
| Brand-axis semantic, role `public` | `brand-<id>.css` of every brand | Brand rule | `var()` of a primitive, of an invariant semantic token or of another declaration of the same brand's rule (DEP-01) |
| Brand-mode source, role `brand-mode-source` (`brand.<category>….<mode>`) | `brand-<id>.css` of every brand | Brand rule | Same as the previous line |
| Mode-axis semantic | `base.css` | Resolver | Toggle form (§7) |
| Invariant semantic | `base.css` | Resolver | `var()` or composite value with `var()` |
| Component | `base.css` | Resolver | `var()` or composite value with `var()` |
| Private mode toggle | `base.css` | Mode rules | Literal `initial` or empty (§6) |

**Primitive partition** (D7). A primitive P is exclusive to brand X when (a) there is at least one
non-primitive token that depends on P, directly or transitively; (b) every non-primitive token that
depends on P belongs to the context of brand X (brand-axis token or brand-mode source of X); and (c)
every primitive that depends on P is also exclusive to X. The remaining primitives, including those
with no reference, go into `base.css`. Primitives are invariant (D7): they have the same value in every
permutation, and the partition only decides in which file the declaration appears. Consequences:
`base.css` never references an exclusive primitive; the only brand-file declarations that `base.css`
references are those with names present in every brand file (brand-axis tokens and brand-mode sources).

**Dependency restrictions imposed by the output form.** The source already guarantees them
([token-source.md](token-source.md), sections 7.2 and 7.3); the build checks them again at output
(`css-scope-dependency`, §13):

- **DEP-01** Declarations of the brand rule depend only on primitives, invariant semantic tokens and
  other declarations of the same brand's rule; never on a mode-axis token nor on a component (AX-2,
  `TKN-AXIS-DEPENDENCY`). The brand rule is not re-evaluated in a mode-only scope, and a mode
  dependency would freeze the current mode in the brand scope. Reading an invariant token in the brand
  scope is safe: it depends on no axis (AX-1) and the resolver declares it on the same element.
- **DEP-02** Resolver tokens reference a brand-mode source only inside the toggle form of the
  corresponding mode-axis token, with the mode suffix equal to the toggle's mode (V-08). No invariant
  or component token references `brand.…` (`TKN-BRAND-SOURCE-REF`).
- **DEP-03** Every whole-token alias becomes `var(--<prefixo>-<target>)` without a fallback. An alias
  in a composite subvalue becomes `var()` at the subvalue's position. `$ref` (only in the primitive
  layer, V-05) is resolved in the build and emitted as a literal.
- **DEP-04** Each published token corresponds to exactly one custom property, named `--<prefixo>-`
  followed by the path segments joined by `-` (e.g. `color.bg.surface` → `--<prefixo>-color-bg-surface`;
  `brand.color.bg.surface.light` → `--<prefixo>-brand-color-bg-surface-light`). A CSS name collision
  between distinct paths is a validation error (`TKN-NAME-COLLISION`). Public segments are lowercase
  ASCII kebab without `_`, so the private space `--<prefixo>-_*` is disjoint by construction.

The manifest `dist/meta/tokens.manifest.json` ([build-manifests.md](build-manifests.md)) MUST expose,
per token, `cssName` and `placement`
(`base`, `brand` or `brand-exclusive`, with `exclusiveBrand` in the last case). These fields feed the
style lint, the browser tests (§16) and the ENG-06 check.

## 5. Selectors and specificity levels

The generated CSS uses only the selectors below; any other is a violation (`css-brand-selector` or
`css-syntax`).

| Level | Selector | Specificity | File | Declares |
| --- | --- | --- | --- | --- |
| N0 | `:where(:root)` | (0,0,0) | `base.css` | Shared primitives |
| N0 | `:where(:root)` in the default mode rule | (0,0,0) | `base.css` | Default mode toggles and `color-scheme` |
| N0 | `:where(:root, [data-<prefixo>-brand], [data-<prefixo>-mode])` | (0,0,0) | `base.css` | Resolver |
| N0 | `:where(:root)` in the default brand rule | (0,0,0) | `brand-<default>.css` | Default brand values |
| N1 | `[data-<prefixo>-mode="light"]`, `[data-<prefixo>-mode="dark"]` | (0,1,0) | `base.css` | Mode toggles and `color-scheme` |
| N1 | `[data-<prefixo>-brand="<id>"]` | (0,1,0) | `brand-<id>.css` | Values of brand `<id>` |

Why source order does not matter (U-03):

1. The properties declared in `base.css` and in the brand files are disjoint
   (`css-base-brand-value`), so the relative position between `base.css` and the brand files is
   indifferent.
2. Among brand files the brand-axis names repeat, but on the same element at most one N1 brand rule
   matches, because the attribute has a single value, and it wins over any N0 rule. The only N0 brand
   rule is that of the default brand's file, and there is a single default brand.
3. The toggles are declared by an N0 rule (`:where(:root)`) and by N1 mode rules, and an element
   matches at most one mode rule.
4. Files imported twice repeat identical declarations.

## 6. Private mode toggles

- **T-01** For each mode `<m>` of the `mode` modifier there is a toggle `--<prefixo>-_on-<m>`. In the
  current version: `--<prefixo>-_on-light` and `--<prefixo>-_on-dark`.
- **T-02** A toggle that is on equals the literal `initial` (a guaranteed-invalid value, which makes
  `var()` use the fallback). A toggle that is off equals empty, written `--<prefixo>-_on-<m>: ;` (the
  empty value is valid in css-variables-1 and substitutes nothing). In each mode rule, exactly one
  toggle is on.
- **T-03** The toggle value is always literal. It is NEVER assigned by indirection, like
  `--<prefixo>-_on-light: var(--something-that-equals-initial)`, because WebKit does not produce the
  guaranteed-invalid value in that case (bug 243247, open).
- **T-04** Toggles are declared only in the mode rules of `base.css`: the default mode rule, whose
  selector is `:where(:root), [data-<prefixo>-mode="<default>"]`, and a rule
  `[data-<prefixo>-mode="<m>"]` for each other mode. Those rules also set
  `color-scheme: <m>`, the only standard (non-custom) property of the token CSS, so that native
  controls follow the mode of the subtree.
- **T-05** The toggles are private: they are outside the ESM, the `.d.ts`, the API report, the DOM
  contract, the design-tool sync and the definition of "variable without a value" (§10.1). Apps MUST
  NOT read, declare nor register (`@property`) `--<prefixo>-_*` variables.

## 7. Resolver

- **RS-01** The resolver is a single rule in `base.css`, with the exact selector
  `:where(:root, [data-<prefixo>-brand], [data-<prefixo>-mode])`. It matches the root and every element
  that has one of the attributes, with a valid value or not; those elements are the theme scopes.
- **RS-02** The resolver declares every mode-axis semantic token, every invariant semantic token and
  every component token. None of those tokens is declared elsewhere. Invariant tokens do not depend on
  an axis (AX-1) and would work on the root, but they sit in the resolver as per D3: there is a single
  rule for everything that is not brand-related, and changing a token's axis between invariant and mode
  does not move the declaration.
- **RS-03** A mode-axis token uses the toggle form, with the modes in canonical order (default mode
  first, then the rest by code point; today `light`, `dark`) and no character between the `)` of one
  toggle and the `var(` of the next:

  ```css
  --<prefixo>-color-bg-surface: var(--<prefixo>-_on-light, var(--<prefixo>-brand-color-bg-surface-light))var(--<prefixo>-_on-dark, var(--<prefixo>-brand-color-bg-surface-dark));
  ```

  Each fallback is the serialized value of that mode. A space separating the toggles would appear in
  the computed value (`"#ffffff "`), breaking exact comparison, reading by JavaScript and style
  queries; the space-free form was verified in Chromium, Firefox and WebKit, with and without
  minification (research/css-scopes.md, re-verification).
- **RS-04** An invariant or component token uses the serialized value directly (alias as `var()`).
- **RS-05** Why it works: the computed value of a custom property is the specified value with the
  `var()` substituted, and it is that value which inherits (css-variables-1). The brand rule's
  declarations come from the nearest brand scope; the toggles come from the nearest mode scope; and the
  resolver recomputes all tokens in every scope of any axis. Thus, for each axis, the nearest scope
  applies (FR-012), and "each scope redeclares the semantic tokens" (TOK-14) holds literally. A
  component alias is also recomputed in each scope, which is why component tokens are never frozen in an
  outer scope.
- **RS-06** The mechanism works for any token type (color, multi-layer shadow, opacity, dimension),
  because the toggle chooses the whole value.

Reading the sketch:

- `color.neutral.*` is used by both brands and by `color.fg.default` (outside the brand axis), so it
  sits in `base.css`. `color.blue.*` and `radius.2` are exclusive to `a`; `color.green.*` and
  `radius.4`, to `b`; each group sits in its brand's file.
- `brand-a.css` and `brand-b.css` declare the same set of brand-axis names and brand-mode sources
  (structural parity, TOK-09); only the exclusive primitives differ.
- `color.bg.surface` varies by brand and by mode, so it is a mode-axis token whose value in each mode
  is an alias to the brand-mode source (FR-033). The resolver recomputes it in every scope with the
  toggles of the nearest mode scope and the sources of the nearest brand scope.
- The resolver references `--<prefixo>-color-bg-accent`, `--<prefixo>-radius-control-default` and the
  `--<prefixo>-brand-…` sources, declared in every brand file; that is why `base.css` does not work
  without a brand file (U-01).
- `color.card.bg.default` is a component alias to a mode-axis token; in a mode-only scope, it follows
  the new mode because it is also recomputed there.
- The sketch format is normative regarding whitespace and order: fixed header, two-space indentation,
  one declaration per line, `name: value;`, a blank line between rules, rules in the order primitives →
  mode rules (default first) → resolver, declarations ordered by code point and a file ending with a
  line break.

## 9. Attribute API and resolution rules

| Attribute | Valid values | Where | Effect |
| --- | --- | --- | --- |
| `data-<prefixo>-brand` | Id of a brand whose file the page imported (in the fixtures: `a`, `b`) | Any element | Brand of the element and of the subtree |
| `data-<prefixo>-mode` | `light`, `dark` | Any element | Mode of the element and of the subtree, including `color-scheme` |

- **R-01** Brand and mode are independent axes: any brand combines with any mode, and an element MAY
  have both attributes, one of them or none (FR-010).
- **R-02** For each axis the nearest scope of that axis applies, on the element itself or on the
  nearest ancestor with a valid value (FR-012). A scope that defines only the mode inherits the brand
  from the ancestor, and vice versa.
- **R-03** With no valid mode attribute on the element nor on an ancestor, the default mode (`light`,
  spec assumption) applies. With no valid brand attribute, the default brand applies (designated by the
  requester, CMP-24; `a` in the fixtures), provided its file is imported; otherwise U-02 applies
  (FR-013).
- **R-04** An invalid value is ignored on that axis: the element remains a scope (matches the resolver)
  and recomputes the tokens from the inherited inputs, keeping the values of the nearest ancestor,
  without a variable lacking a value (FR-014). Invalid values are: a nonexistent id, an empty value, a
  mode outside the list and a brand id whose file was not imported.
- **R-05** Value comparison is exact: case-sensitive (`Dark` is invalid) and without trimming spaces
  (` dark` is invalid).
- **R-06** Setting, switching or removing attributes at runtime updates the values without reloading
  the page and without PatoDS code, because the mechanism is CSS only (FR-018). For the same reason,
  server HTML with the attributes already produces the correct values, without JavaScript.
- **R-07** Effective value of an axis on an element: the value of the nearest ancestor (including the
  element itself) whose attribute of that axis has a valid value; with none, the default of R-03. That
  is the definition of the test oracle (§16).

## 10. Operational definitions

### 10.1 Variable without a value

Per the spec Clarifications section (interpretation to be confirmed with the acceptor): it is a public
token `--<prefixo>-*` (name without the private segment `_`) that is empty or guaranteed-invalid, or a
`var()` without a fallback that resolves that way. The private toggles `--<prefixo>-_on-*` are empty or
`initial` by design and are excluded. Verification:

- **Static** (`css-var-undeclared`): every `var()` without a fallback in the published CSS points to a
  declaration that exists in the file itself; or, from a brand file, in `base.css`; or, from
  `base.css`, in every brand file (brand-axis names and brand-mode sources). With U-01 and U-02, every
  reference has an applicable declaration on every element. The only `var()` with a fallback are the
  toggles.
- **In-browser** (BR-18): in every supported configuration (U-01 and U-02), for every element E with
  effective brand b and effective mode m (R-07), and for every token N of the map `values[b][m]` except
  the primitives exclusive to another brand, `getComputedStyle(E).getPropertyValue(cssName(N))` is
  non-empty and equal, without trimming, to `values[b][m][N]` from the tarball.

### 10.2 Only selectors of that brand

- In `brand-X.css`, every style rule has the exact selector `[data-<prefixo>-brand="X"]` or, only in
  the default brand's file, `:where(:root), [data-<prefixo>-brand="X"]`. There is no other selector,
  combinator, pseudo-class, mode attribute nor attribute with another id.
- The only brand-neutral content allowed in a brand file is the layer-order declaration and the
  `@layer` block, which are not selectors.
- `base.css` has no selector with a brand value; the brand attribute appears in it only by presence,
  inside the resolver.

### 10.3 Variable exclusive to a brand

A custom property declared in `brand-X.css` and in no other published file. Per §4, these are exactly
the exclusive primitives of X; the brand-axis names and brand-mode sources exist in every brand file
and are not exclusive. The example app that imports `base.css` and only `brand-a.css` (FR-017) is
verified this way: the production bundle CSS contains no name exclusive to another brand nor a selector
`[data-<prefixo>-brand="<other id>"]`, and BR-18 passes.

## 11. Value serialization

All serialization is done by the tooling package and is the same in the CSS, in the ESM values map
(`./values`) and in the contrast check.

| DTCG `$type` | Emitted form |
| --- | --- |
| opaque `color` (alpha 1 after quantization) | `#rrggbb`, six lowercase hexadecimal digits |
| `color` with alpha < 1 | `rgb(r g b / a)`, with r, g and b integers from 0 to 255 and `a` with exactly three decimal places (e.g. `rgb(0 0 0 / 0.400)`) |
| `dimension` | Number followed by the source unit (`px` or `rem`), always with a unit, including zero (`0px`) |
| `duration` | Number in `ms` (a source in `s` is converted) |
| `number` | Number |
| `fontWeight` | Number from 1 to 1000 (DTCG names converted to the corresponding number) |
| `fontFamily` | Names separated by `, `; generic CSS keywords without quotes, other names in double quotes with `"` and `\` escaped |
| `cubicBezier` | `cubic-bezier(x1, y1, x2, y2)` |
| `strokeStyle` (keyword) | The keyword (`solid`, `dashed`, etc.) |
| `border` | `<width> <style> <color>` |
| `shadow` | `[inset ]<offsetX> <offsetY> <blur> <spread> <color>`; comma-separated list in source order |
| `transition` | `<duration> <timingFunction> <delay>` |

Rules:

- **S-01 Color** (D5): the DTCG components are the source of truth. The emitted value is the output of
  `toEmittedSrgb()` of the `@<prefixo>/color` package: conversion to sRGB and gamut mapping by the
  CSS Color 4 algorithm (method `css`, deltaEOK with JND 0.02, always passed explicitly), followed by
  8-bit quantization. The alpha is quantized to three decimal places; if the result is 1.000, the
  opaque form is emitted. Named colors, `transparent`, `oklch()` and `color(display-p3 …)` are not
  emitted. The contrast checker composes with the alpha read back from the emitted string, so that the
  measured value is the emitted value.
- **S-02 Numbers**: decimal notation without an exponent, without `+`, without trailing zeros, with a
  zero before the dot (`0.5`) and `-0` written `0`. A value that would require an exponent or more than
  four decimal places is rejected at validation, instead of being silently rounded.
- **S-03 Aliases**: an alias becomes `var(--<prefixo>-<target>)` (DEP-03). The ESM values map always
  carries the final resolved value, without `var()`, which equals the computed value of the custom
  property in the browser.
- **S-04 No faithful serialization**: composite `$type` `typography` and `strokeStyle` in object form
  have no lossless single-CSS-value representation (the `font` shorthand does not carry `letterSpacing`
  and resets other subproperties). Since each token corresponds to exactly one custom property
  (DEP-04), the build rejects those values in a published token (code `unserializable-value`, exit 1),
  and typography is published through atomic tokens (`fontFamily`, `fontWeight`, `dimension`,
  `number`), which the source grammar already provides for (`typography.family`, `.weight`, `.size`,
  `.line-height`, `.letter-spacing`). See §17, P-02 (decided).
- **S-05** The serializers of `@terrazzo/token-tools/css` MAY be reused where the output coincides
  byte-for-byte with this contract; if there is a difference, the contract prevails, and the tooling
  package's golden outputs detect the change on each update (D1).

## 12. Determinism

Two builds of the same source produce byte-for-byte identical CSS (FR-015, SC-002).

- **D-01** Files in UTF-8 without BOM and without `@charset`, with LF line endings and one final line
  break.
- **D-02** Fixed header, identical in every file, with no date, version, path or environment data.
- **D-03** Declarations ordered by name, by code point, never by locale. Brands processed by id, by
  code point. Modes in the canonical order of RS-03. Fixed rule order (§8).
- **D-04** Fixed formatting (§8); the published output is not minified and has no source map.
  Minification is the app's job; the minified variant is part of the tests (BR-19).
- **D-05** An empty rule is omitted.
- **D-06** `dist/css/` is cleaned before each build: there is exactly one `brand-<id>.css` per brand of
  the resolver, with no residual file.
- **D-07** Numbers and colors follow §11, without locale-dependent formatting; the color passes through
  the same exact version of `colorjs.io`, with the gamut method always explicit.
- **D-08** Generation does not depend on the parser's iteration order: the internal model is ordered
  before serialization.
- **D-09** `pnpm check:determinism` compares the sha256 of each file and of the tarballs between two
  builds in clean worktrees, under different paths, `TZ` and `LC_ALL`, with no task cache, packaging
  with `pnpm pack`; nightly, also between runners and between the floor Node and the latest of the
  matrix (D1, D6).

## 13. Checks of the generated CSS

The checks run inside `tokens-build build` (script `pnpm tokens:build`), after generating the content
in memory and before writing `dist/`. With any violation, the build exits with code 1, writes no
artifact and reports each finding with the generated file, line and column, plus the token and the
source location (`file:line:column`) when there is one; with `--json`, the findings go to stdout in a
stable schema. A configuration error (for example, invalid `layers.json`) exits with code 2, and an
internal error with code 3. Each code has at least one deliberate violation fixture in the unit tests
of `tools/tokens-build` (QA-02, SC-009).

The codes are the same as in [tools-cli.md](tools-cli.md), §2.2, which also lists
`unserializable-value` (S-04) and `private-segment-leak` ([esm-output.md](esm-output.md), E-08).

| Code | Rule checked |
| --- | --- |
| `css-layer` | Every style rule sits inside `@layer <prefixo>.tokens`; the layer-order declaration is the first statement of every file, identical across all and identical to the single source (L-01 to L-03) |
| `css-toggle-form` | Every mode-axis token is in the RS-03 form (one toggle per mode, in canonical order, with no character between the toggles); every toggle equals literally `initial` or empty, never `var()`; exactly one `initial` per mode rule; toggles only in the mode rules of `base.css` (T-02 to T-04) |
| `css-var-undeclared` | Every `var()` target has a declaration per §10.1 (static check) |

## 14. Consumer override

Supported patterns:

- **O-01** Override outside a layer (or in a layer declared after `<prefixo>.tokens`). CSS in a layer
  before the tokens layer loses.
- **O-02** To override a semantic token in an area, declare the override on the scope element itself
  (the root or an element with `data-<prefixo>-brand` or `data-<prefixo>-mode`). On that same element,
  the resolver's component aliases start using the new value, and descendants inherit both.
- **O-03** To change a specific component, override the component token directly, on any element.
- **O-04** Theme scopes nested below an override recompute the tokens and undo it: a nested scope is a
  new theme, by design. To keep the override, repeat it in the inner scope's selector.
- **O-05** Overriding primitives is possible (the aliases are recomputed from the inherited value), but
  it is not a theme API: it affects all brands and has no value-stability guarantee.
- **O-06** To style with tokens, use `var(--<prefixo>-…)` or the ESM references; the ESM values map
  does not follow scopes and is not meant for styling the DOM.
- **O-07** An app that sets `color-scheme` outside a layer wins over the token's; this is allowed, but
  then native controls stop following the PatoDS mode.

## 15. Known limitations

- **Aliases frozen on an element that is not a scope**: overriding a semantic token on an element
  without a theme attribute changes the token for descendants, but not the component aliases, which
  were computed in the nearest scope and inherited as a value (verified in the three engines). Use O-02
  or O-03.
- **Portals**: a portal container outside the origin subtree receives the values of its own place in
  the DOM. It must carry the two attributes with the origin's effective values (R-07), the
  responsibility of the theme Provider in the components feature (CMP-21).
- **Exclusive primitive**: a reference to a primitive exclusive to brand X only resolves inside a scope
  of X with `brand-X.css` imported. Component styles do not use primitives (TOK-03).
- **App with a non-default brand only**: requires the brand attribute on the root (U-02).
- **Shadow DOM and iframes**: the token CSS in the document does not match elements inside shadow
  roots, and each iframe is a separate document, with its own imports and attributes. Web Components
  are outside the contract (constitution).
- **Registered custom properties**: registering `--<prefixo>-*` with `@property` changes inheritance
  and serialization and may break the toggles; it is not supported.
- **Breakpoints**: tokens of the `breakpoint` category are emitted as custom properties, but `var()`
  is not valid in `@media`; use in media queries depends on the core mechanism (core feature).
- **DevTools**: the specified value appears as a chain of `var()`; the computed value is the final one.
- **One version per document**: two versions of the package on the same page compete for the same
  names.
- **New mode**: requires regenerating the resolver and changes the API (major, data-model).
- **Size**: about 5.6 KB gzip per brand file with 350 synthetic tokens in the original design; the
  split into `base.css` changes the distribution and should be measured against the QA-07 budget, whose
  value is pending in the thresholds assumption.
- **Compatibility**: the mechanism uses only custom properties, `var()` fallback, `:where()` and
  `@layer`, which requires nothing beyond the `@layer` already required by ADR-03. The browser list
  remains an open decision (assumption ENG-08); the ENG-08 CSS compatibility lint validates the adopted
  list, and the real-browser tests run in its engines. The minified empty form `--x:;` is part of the
  matrix (BR-19).
- **`if()` in the future**: when broad support exists, the generator MAY swap the toggles for `if()`
  without changing the attribute API; the bytes change and the full engine matrix runs again.

## 16. Real-browser tests

Run with `@playwright/test` against the example app `@<prefixo>/tokens-example`
(`apps/tokens-example`, Vite 8 without a framework), built only from the packaged tarball and served
by `vite preview`, with no external network (`pnpm test:e2e`; tests in
`apps/tokens-example/tests`). Chromium on every PR; every engine of the browser list nightly and
before publishing (QA-12, assumption ENG-08; the research used Chromium, Firefox and WebKit).

- **Expected values** come from the `values` map and from the tarball manifest, never hand-written.
- **Oracle**: for each element, the effective brand and mode per R-07, considering the brands imported
  in the configuration.
- **Comparison**: custom properties by exact string equality, without trimming; used values
  (`background-color`, `box-shadow`, `border-radius`, `outline-color`, `height`) against the reference
  literal normalized by the browser itself on a probe element.

| Case | Configuration | Expected |
| --- | --- | --- |
| BR-01 | No attributes; `base.css` + default brand | Root and descendants with the default brand and `light` |
| BR-02 | Only `data-<prefixo>-mode="dark"` on the root | Default brand and `dark` across the whole tree |
| BR-03 | Mode-only inner scope: `a`-`light` > `[mode=dark]` | The element and the child in `a`-`dark`; the next sibling returns to `a`-`light` |
| BR-04 | Brand-only scope inherits the mode: `a`-`dark` > `[brand=b]` | `b`-`dark` on the element and on the child |

| BR-06 | Alternating mode `light` > `dark` > `light` | Each level with its mode |
| BR-07 | Chain `dark` > `b` > `a` > `[mode=light]` > `[brand=b]` > `[mode=dark]` | Correct value at each level |
| BR-08 | Both attributes on the same element and the swapped pair nested within it | Each element with its combination |
| BR-09 | Brand-only scope at the top, with no mode ancestor | That brand with `light` (default of `base.css`) |
| BR-10 | Invalid values: brand `zzz`, empty brand, mode `sepia`, empty mode, `Dark` and ` dark` | The element keeps the value of the nearest valid ancestor on that axis |
| BR-11 | Brand present in the markup without its file imported | Same as an invalid value |
| BR-12 | Sibling after an already-closed nested scope | Values of the outer scope |
